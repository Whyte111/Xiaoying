# 04 · AI 使用记录

## 用在哪

本项目的以下部分由 AI 起草，人工在关键分岔点做决策与验收：

| 阶段 | AI 产出 | 人做了什么 |
|---|---|---|
| 需求澄清 | 把题目拆成可执行的问题定义（交付物/硬约束/隐含要求/完成标准/风险） | 确认口径，补"先确认文件再读"的约束 |
| 方案选型 | 4 个候选方案 + 对比矩阵 | **选定方案 A（手写显式循环）**，否决框架与固定分支 |
| 系统骨架 | 分层、接口、数据结构、主链路 | 逐条拍板 7 个边界（见下） |
| 实现 | 约 900 行代码 + 89 项测试 + 6 个场景 | 要求"分模块做一步验一步""规格冲突先指出不要默默删" |
| 审计 | 以 QA/安全视角自检，发现 12 类问题 | 要求先列问题再给最小修法 |
| 交付 | README 与 5 份文档 | 要求"文档必须与真实一致" |

## 人拍板的关键决策

1. 选**手写 ReAct 循环**而非 LangGraph，理由是"稳交付 > 炫技"。
2. 7 个边界：`rewrite_query` 与 `ask_clarify` 拆成两个动作、分镜时长由工具反算、超时长最多修正 3 次、未给素材必须先检索、语速默认 4.5 字/秒、规则文件缺失时 fail-closed、必填字段为 topic/platform/target。
3. 要求**撤回** AI 自行加的"时长不低于目标 80%"约束——它导致模型震荡，且题目并未要求。
4. 要求把"压缩"从模型自由改写改成**确定性工具**，理由是证据不可复现。
5. 要求交付前做一次"不默认结果正确"的自检。

## AI 犯过、被人纠正的错

| 问题 | 纠正方式 |
|---|---|
| 骨架漏了"写脚本"动作，闭环接不上 | 开工前指出，补 `compose` |
| 自行添加"80% 时长"约束导致震荡 | 撤回该约束 |
| 三次把观察写得不可行动（只报"未通过"） | 改为回传可用事实与删减字数 |
| 压缩工具报"计划时长"而非实际时长 | 改为按裁剪后实际值上报 |

## 验证方式

- 每个模块完成即跑对应测试，不攒到最后；
- 新增规则先写会失败的测试（红），再改代码（绿）；
- 用变异测试确认断言有效（改坏一处，14 条变红）；
- 用真实模型跑 6 个场景，产物留在 `examples/`。

## 说明

AI 负责产出与执行，**判断与取舍由人负责**。文档中的数字（89 项测试、各场景状态、耗时）都取自实际运行，未做修饰。
