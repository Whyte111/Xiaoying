# 方案对比 · 题目四：短视频脚本 Agent

> 前置：本文不含代码。真实模型可用（据你口述 `.env` 中有 DeepSeek key，**未读取该文件**）。
> 评价权重按要求设定：**稳交付 > 技巧炫技**。$T$ 为 3 小时预算。

---

## 方案 A：手写显式 ReAct 单循环（无框架，限定动作空间）

### 1. 大致怎么做

一个 `while` 循环，模型每轮只输出结构化动作：

```
{ "decision_basis": "...", "action": "search|ask_clarify|estimate|check_rules|finish", "args": {...} }
```

- **动作空间限定 5 个**：`search_material`（检索素材）、`ask_clarify`（请求补充/改写查询后重搜）、`estimate_duration`、`check_rules`、`finish`。
- **三个工具全部确定性纯函数**：素材检索（关键词匹配本地 `data/`）、时长估算（字数 ÷ 语速，固定公式）、规则检查（可枚举禁用词/必提项/时长上限 → pass-fail 列表）。
- **分发器**：解析模型动作 → 调工具 → 把返回摘要 append 进 `observations` → 回灌模型 → 下一轮。
- **三重刹车**：最大步数（如 8）、最大工具调用（如 10）、**同动作同参数重复检测**；触顶写 `status=incomplete` + `reason`。
- **Trace 由循环自己写**：每步 `{step, action, args, result_digest, next_decision, decision_basis}` 落到 `examples/*.jsonl`，模型不参与记录。
- **模型适配层**：一个 `ModelClient` 接口，真实 DeepSeek 与离线 Mock 两个实现，**同一循环**。

### 2. 主要优点
- 与验收原文 A1–A5 **逐条对齐**，"模型选动作→执行→观察→调整"在代码里肉眼可见，评审不需要猜。
- Trace 天然是运行时产物（解 I6），且字段可自定，`decision_basis` 想加就加。
- 零框架依赖 → 无版本/环境风险，评审 clone 即跑。
- 三个工具纯函数，可单测性拉满。

### 3. 主要风险
- **模型不守格式**：返回非 JSON 或动作不在枚举内 → 需 schema 校验 + 1 次"格式纠错"重试，仍失败则记为 `tool_error` 态（正好当工具失败场景用）。
- **模型偷懒早停**：第一轮直接 `finish` → 需在 prompt 里硬性要求"未经过 estimate + check_rules 不得 finish"，并在分发器里做**前置条件校验**（不满足则驳回并回灌错误）。
- **循环打转**：重复动作 → 靠重复检测 + 步数上限兜底。
- DeepSeek 的 JSON 输出/function calling 稳定性**待实测**，不能预设。

### 4. 实现的复杂度
**低（约 300–450 行核心）**。无学习曲线，主要工作量在 prompt 打磨和 5 个场景的数据准备。
时间预算：数据+规则 0.5h / 循环+工具 1h / 测试 0.5h / 5 场景 trace 0.5h / 文档 0.5h ≈ **3h 紧但可控**。

### 5. 可测试性
**高，且是三层结构**（正好对应"用测试证明效果"）：
- 工具层：纯函数断言，输入→输出完全确定。
- 循环层：注入 `FakeModel`（脚本化动作序列），断言**决策转移**，例如"检索返回空 → 下一步 action == ask_clarify 而非 finish"、"达上限 → `status == incomplete`"。
- 端到端：真实模型跑 5 场景，断言脚本结构 + 事实可追溯 + 时长复算一致。

## 方案 B：框架托管（LangGraph / AgentScope / Google ADK）

### 1. 大致怎么做
用框架的 StateGraph 或内置 ReAct Agent，把三个工具注册为 tool，由框架负责循环、状态与中断。自己只写节点与 prompt。

### 2. 主要优点
- 循环、状态机、重试样板由框架承担，代码量表面更少。
- 文档能写"框架版本 + 用到的功能 + 承担职责"，符合 D1/D2 的加分项。

### 3. 主要风险
- **学习曲线直接吃掉 3h 预算**（图结构、状态定义、事件流），这是最大的时间风险。
- **Trace 不归你管**：框架的 event/step 结构未必含"决策依据"，要自己二次抽取，且格式脆弱。
- 容易出现"框架默认 ReAct，你只是把工具挂上去"，被追问"你改了什么"时答不出（D1 明确说框架名不加分）。
- 依赖/版本/离线安装风险，评审环境跑不通的概率显著高于 A。

### 4. 实现的复杂度
**中偏高**。代码行数或许更少，但**有效工时更高**，且不确定性集中在"能不能调通"。

### 5. 可测试性
**中**。节点可单测，但断言行为要穿透框架抽象，测试与框架版本耦合，脆弱。难写出"因工具结果不同而改变动作"的清晰断言。

## 方案 C：确定性骨架 + 模型只在分叉点决策

### 1. 大致怎么做
代码写死主流程：`检索 → 估算 → 检查 → 输出`，模型只在 3 个分叉处被问一次"选哪个"：检索空时改写查询还是请求补充；超时长时压缩还是声明无法满足；规则违规时改哪个分镜。

### 2. 主要优点
- **最可控**，路径完全可枚举，测试最容易写。
- token 消耗最低，最省时。

### 3. 主要风险
- **踩 A2 红线**：需知原文"允许预设流程作为执行骨架"，但紧接着说"仅有固定条件分支…不视为完成"。骨架一旦写死到"每步顺序不变、模型只答选择题"，评审极可能判定为**假 ReAct**——这是本题第一大翻车点。
- 要洗脱嫌疑，反而需要额外证明"同一分叉因不同观察选了不同动作"，工作量回补。

### 4. 实现的复杂度
**最低（约 150–250 行）**。

### 5. 可测试性
**极高**，但测得再全也救不回合规性——**可测试性高 ≠ 能得分**。

---

## 方案 D：Plan-then-Execute 两段式（含多 Agent 变体）

### 1. 大致怎么做
第一轮让模型一次性产出完整计划 + 各分镜草案，代码执行并汇总；第二轮把检查结果回灌，模型整体改写一次。多 Agent 变体再拆 Planner / Writer / Checker。

### 2. 主要优点
- token 少、延迟低、输出连贯性好。
- 多 Agent 版本"看起来"完整。

### 3. 主要风险
- 只有 2 轮交互，**不足以构成"观察→调整→再观察"的循环**（A1 要求"循环"，A3 要求 ≥2 条路径体现调整）。
- 多 Agent 在需知里**明确非必需、不加分**，是纯时间黑洞。
- 时长的二次修正容易变成"模型自己报个 28 秒"，撞 I1（估算不可复算）。

### 4. 实现的复杂度
两段式 **低**；多 Agent 变体 **高且无收益**。

### 5. 可测试性
两段式**中高**；多 Agent **低**（跨 agent 断言成本翻倍）。

## 推荐：方案 A，并吸收 C 的一个优点

**选 A（手写显式循环 + 限定 5 动作 + 确定性工具 + 三重刹车）。**

理由，按"稳交付"逐条：

1. **合规风险最低。** 本题的否决项不是"做得不够炫"，而是"被判定假 ReAct"。A 把循环摆在你自己的代码里，评审读 30 行就能确认——这是唯一不需要解释的证明方式。
2. **证据风险最低。** Trace 由循环落盘、字段自定，`decision_basis` 天然可写；B 需要从框架事件里二次抽取，属于"为了省事反而多干活"。
3. **环境风险最低。** 零框架依赖意味着 README 里的命令在评审机器上失败的概率最小。**3 小时预算里，"能跑通"比"架构漂亮"值钱一个数量级。**
4. **测试与验收天然同构。** 三层测试（工具纯函数 / FakeModel 测决策转移 / 真模型端到端）正好逐条覆盖 5 个验收场景与 A3 的"两条路径"，写测试不是额外负担，而是产出证据本身。
5. **A 的软肋正好被 C 的优点补上。** A 的最大风险是"模型乱来"，解法不是加骨架，而是**缩小动作空间**——只给 5 个白名单动作 + 前置条件校验（未经 estimate/check_rules 不得 finish）+ 重复动作检测。这保留了"模型自由选择"的合规性，同时拿到了 C 的可控性。**动作空间限定，不等于流程写死。**

**为什么不选其他：**

- **不选 B**：它把不确定性从"写逻辑"转移到"调通框架"。3 小时里框架学习是唯一可能让你交付不出来的单项，而框架名本身不加分（D1 原文）。用框架还要额外论证"我改了什么"，等于多一道答辩题。
- **不选 C**：它是"最省事的错误答案"。可控性极好，但恰好撞在 A2 的红线上——固定条件分支不视为完成。把最稳的做法做成最不达标的做法，是典型的优化错了目标。它的可控性我用"限动作空间"拿到了，不需要付出合规代价。
- **不选 D**：两段式轮次不足，难以证明"观察后调整"；多 Agent 被需知明确标注非必需且不加分，多 Agent 的复杂度换不来任何评分。

**退路**：若真实模型在 1.5h 处仍调不稳（JSON 不守格式反复失败），**不要换架构**，把 `ModelClient` 切到离线 Mock 继续跑通全链路，在 `03-evaluation.md` 里如实写"Mock 只验证流程、不证明真实模型决策效果"（需知原文允许），并保留已跑出的真模型 trace。这样丢掉的是"真实模型效果"分，保住的是"结构完整"分。
