# 02 设计

## 一句话

**模型负责决策与措辞，代码负责判定与兜底。**

模型可以自己觉得"没冲突"、自己觉得"引用没问题"，但最终状态由确定性代码裁决。这是整套设计的主轴。

## 核心结构

```
CLI (cli.py)
  └── Agent (agent.py)  ← 唯一持有循环的地方
        ├── LLMClient  (llm.py)    DeepSeek / FakeLLM
        ├── Toolbox    (tools.py)  search / read_doc / ask_user / finish
        │     └── Retriever (retrieval.py)  jieba + BM25  (corpus.py)
        ├── conflict   (conflict.py)  冲突检测，确定性
        ├── answer     (answer.py)    引用校验 + 状态裁决
        ├── session    (session.py)   多轮上下文
        └── Tracer     (trace.py)     JSONL 落盘
```

循环每一轮：拼上下文 → 模型输出 JSON 决策 → 执行工具 → 观察回灌 → 判断终止。

## 关键取舍

**1. 不用 Agent 框架，手写循环。**
框架抽象会把"固定图"和"模型决策"混在一起，评审很难判断到底是不是真 ReAct。手写循环只有几十行，决策来源一目了然；代价是错误处理要自己写。

**2. 判定权在代码，不在模型。**
三处硬兜底：
- 冲突：检索命中即检测，模型想直接答也不行，门禁会改写状态；
- 引用：逐字校验 + 弱相关性校验，模型编的片段过不去；
- 状态：`TOOL_ERROR > STEP_LIMIT > NEEDS_CLARIFICATION > INSUFFICIENT > ANSWERED` 固定优先级。

这些不是"提示词要求"，是代码里的 `if`，可单测。

**3. 冲突检测用规则，不用模型。**
规则：小节标题相同 **或** 正文实词重叠 ≥ 0.30；且同一单位族（时长/金额/百分比）内数值不同。
用规则是因为它可复现、可写断言；用模型判冲突会变成"每次跑结果不一样"，无法回归。

**4. 引用先验"存在"，再验"相关"。**
存在性：去掉空白后必须是原文子串。
相关性：引用与回答的双向词覆盖率（0.15 / 0.30），或与问题至少 2 个共同词。
第二层是弱启发式，只挡"拿 A 条款答 B 问题"这种粗错，不挡精细的断章取义——这一点在文档里明说，不包装成已解决。

**5. 离线 Fake 与真实模型共用同一条循环。**
`FakeLLM` 只是按脚本吐决策，循环、工具、校验代码完全一致。所以离线跑通不等于流程正确性打折——它验证的是**系统行为**，只是不验证模型能力。

**6. 零第三方依赖。**
评审 `clone` 后直接跑，不用装包、不用配环境。代价是手写了 BM25 和 JSON 解析（约 120 行），可接受。

**7. 失败必须可见。**
工具异常转成 `ok=False` 的观察值，模型看到失败可以换路；连续 3 次系统级失败直接终止并返回 `TOOL_ERROR`，不让它空转到步数上限。业务性失败（文档不存在）不计入这个阈值。

## 状态机

| 状态 | 触发 |
|---|---|
| `ANSWERED` | 至少 1 条通过校验的引用，且不与冲突相关 |
| `NEEDS_CLARIFICATION` | 模型主动追问，或引用触及冲突文档 |
| `INSUFFICIENT` | 无可核验引用 / 资料不足 |
| `TOOL_ERROR` | 模型不可用，或连续 3 次系统级工具异常 |
| `STEP_LIMIT` | 达到步数上限 |

## 为什么不用向量检索

DeepSeek 不提供 embedding 接口，本地向量模型要下载、装 torch，在评审环境是额外风险；而语料只有 3 篇，BM25 足够。检索质量靠"模型自己改写检索词"补，这也是 ReAct 该做的事。
