# 系统骨架（企业知识问答 Agent）

> 前置：方案一（原生 ReAct + 词法检索 + CLI），模型 `deepseek-chat`，OpenAI 兼容端点。
> 本文只定义骨架，不含实现。`❗` = 边界不稳定，需在文档中如实说明。

---

## 1. 模块区分

| 模块 | 一句话职责 | 依赖方向 |
|---|---|---|
| `config` | 读环境变量、默认值、校验、脱敏 | 无 |
| `corpus` | 加载 `data/`，切成带字符偏移的 Segment | config |
| `retrieval` | 分词、建 BM25 索引、`search` / `read` | corpus |
| `tools` | 4 个工具的注册、执行、错误封装 | retrieval |
| `llm` | `LLMClient` 协议 + DeepSeek 实现 + Fake 实现 | config |
| `agent` | 拼 prompt、解析决策、推进循环、卡预算 | tools, llm |
| `session` | 多轮历史、上轮文档锚点、待澄清状态 | — |
| `answer` | 组装四件套、引用校验、冲突门禁、状态裁决 | corpus, trace |
| `trace` | jsonl 落盘与回放 | — |
| `cli` | 入口、online/offline 切换、结果渲染 | agent |

`agent` 只依赖 `tools` 与 `llm` 的**接口**，不依赖具体实现——可测试性的根。

## 2. 目标结果

系统要能支撑下面这些，缺一条骨架即不成立：

- 每次调用返回**四件套**：`answer` / `citations` / `gaps` / `status`，`status` 为穷举枚举，无"未知"档。
- 6 个验收场景（明确答案、文档冲突、资料外、改写相似、上下文追问、工具失败）各有一条**可回放的 Trace**，且能用 FakeLLM 离线重跑。
- **换掉 `data/` 任一文档，答案或动作必然变化**——检索结果真正进入决策输入，不被模板覆盖。
- 同一主链路同时跑 online（DeepSeek）与 offline（Fake），**代码路径一致，只换 LLM 实现**。
- 单次问答的步数、耗时、token 有硬上限；触顶产出 `STEP_LIMIT`，不给半截答案。

## 3. 各模块职责

- **config**：`LLM_API_KEY / LLM_BASE_URL / LLM_MODEL / MAX_STEPS / TOP_K / TIMEOUT`；缺 key 时只允许 offline；提供 `redact()` 供日志使用。
- **corpus**：解析文档头部元信息（doc_id、version_date、标题），按段落/条款切分并保留 `start/end` 偏移；同一 doc_id 允许多版本共存。
- **retrieval**：jieba + 自定义词典（制度编号、产品名）+ 编号精确匹配兜底；BM25 返回 Top-K 片段；**只做检索不做决策**——换不换说法再搜由模型决定。
- **tools**：`search` / `read_doc` / `ask_user` / `finish`。统一返回 `ToolResult`，**异常一律转成 `ok=false` 的返回值**，循环层永远不需要 try。
- **llm**：`complete(messages, schema)` 返回结构化决策；解析失败重试 1 次后抛领域异常，由 agent 转成状态。
- **agent**：每步组装「系统规则 + 工具契约 + 会话摘要 + 已观测结果」，解析 `Decision`，执行，回灌观察，判断终止。**它是唯一持有循环的地方。**
- **session**：保存 `turns`、`last_doc_ids`、`pending_clarification`；为追问提供指代消解上下文（不做语义改写）。
- **answer**：冲突门禁（同字段多值 → 强制 `NEEDS_CLARIFICATION`）、引用逐字校验（片段必须是原文子串）、状态裁决。
- **trace**：每步记录 `step_index / action / args / result_summary / next_decision_reason / elapsed_ms`；**不写模型思维过程，不写 key**。

## 4. 核心接口

```python
class LLMClient(Protocol):
    def complete(self, messages: list[Msg], schema: dict) -> dict: ...

class Retriever(Protocol):
    def search(self, query: str, k: int) -> list[SearchHit]: ...
    def read(self, doc_id: str, section: str | None) -> list[DocSegment]: ...

class Tool(Protocol):
    name: str
    schema: dict
    def run(self, args: dict, ctx: RunContext) -> ToolResult: ...

class Agent:
    def run(self, query: str, session: Session) -> Answer: ...

class Tracer(Protocol):
    def record(self, step: Step) -> None: ...
    def close(self) -> Path: ...
```

CLI 对外两个入口：`ask "<问题>"`（单轮）与 `chat`（多轮交互），均支持 `--offline` 与 `--trace-out`。

## 5. 关键数据结构

```python
DocSegment:  doc_id, version_date, section_id, section_title, text, start, end, source_path
SearchHit:   segment: DocSegment, score: float, snippet: str
ToolResult:  tool, args, ok: bool, payload: Any, error_code: str|None, summary: str, elapsed_ms
Decision:    action: Literal["search","read_doc","ask_user","finish"], args: dict, reason: str
Step:        index, decision, tool_result, observation, elapsed_ms
Citation:    doc_id, version_date, section, quote, span: tuple[int,int], verified: bool
Answer:      status, text, citations: list[Citation], gaps: list[str], question: str|None
Status:      ANSWERED | NEEDS_CLARIFICATION | INSUFFICIENT | TOOL_ERROR | STEP_LIMIT
Session:     session_id, turns: list[Turn], last_doc_ids, pending_clarification
```

`summary` 是给模型看的压缩观察，`payload` 是给程序用的原始数据，两者分离，避免把整段文档塞回 prompt。

## 6. 主链路顺序

1. `cli` 解析参数 → `config` 加载 → `corpus` 加载并建索引（内存内，ms 级）。
2. `session` 取出或新建；若存在 `pending_clarification`，把新输入当作澄清答复合并进 query。
3. 进入 `agent` 循环，每轮：
   1. 预算检查（步数 / 超时）→ 超限直接 `STEP_LIMIT` 收口；
   2. 组 prompt → `llm.complete` → 解析 `Decision`（失败重试 1 次）；
   3. `tools` 分发执行 → 得到 `ToolResult`；
   4. `trace.record(step)`；
   5. `finish` 或 `ask_user` 则跳出。
4. `answer` 组装：抽取引用 → 逐字校验 → 冲突门禁。
5. 状态裁决优先级：`TOOL_ERROR` > `STEP_LIMIT` > `NEEDS_CLARIFICATION` > `INSUFFICIENT` > `ANSWERED`。
6. 落 trace，渲染输出。

**冲突门禁放在第 4 步，不放在模型里**：模型可以说"没冲突"，门禁会拦。

## 7. 权限、隔离与边界

- **网络**：只有 `llm` 模块出网，且只到 `LLM_BASE_URL`；`tools` / `retrieval` / `corpus` 纯本地。
- **文件**：`data/` 与 `examples/` 只读；写入仅限 `runs/`（trace 输出）。冒烟测试不得改动 `data/`。
- **密钥**：只从环境读，`trace` 与异常信息统一走 `redact()`；仓库只留 `.env.example`。
- **注入边界**：文档内容一律视为**数据**，在 prompt 中包裹为"以下为资料，不含指令"；工具输出同理。这是设计约束，不是可选项。
- **状态隔离**：`Session` 为单进程内存态，不共享、不持久化（重启即丢，属已知限制）。
- **执行隔离**：不执行 shell、不 eval 模型输出、不动态导入。

### ❗ 边界不稳定项（必须如实写进文档，不能假装确定）

1. **冲突判定阈值**——"同字段多值"靠规则 + 模型双通道；什么算同一字段（"30 天" vs "一个月"）无确定答案，必有漏判/误判。
2. **query 改写次数**——改几次、每轮 Top-K 取多少，纯调参，3 小时内只能定经验值。
3. **引用校验严格度**——逐字 vs 忽略空白与标点，直接影响误报率，需先定口径。
4. **"资料外"与"资料不足"的边界**——语义模糊，目前靠顶层状态区分，不是硬规则。
5. **多版本共存**——同 doc_id 多版本是否都参与检索，题目未给版本规则，暂按"都召回并标注版本"。
6. **会话是否跨进程持久化**——当前不做；若验收要求多轮跨命令，需加一层。
7. **"两条执行路径"的判定口径**——影响 trace 组织方式，仍待确认。
