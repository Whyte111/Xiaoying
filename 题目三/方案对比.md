# 方案对比（基于已确认的问题定义）

> 前提事实：`.env` 里是 `LLM_MODEL=deepseek-chat`，OpenAI 兼容端点 `https://api.deepseek.com/v1`。
> 关键推论：DeepSeek **不提供 embedding 接口**，向量检索必须走本地模型（需下载），这是本方案取舍的分水岭。
> 本文不含代码。

---

## 方案一：原生 ReAct 循环 + 词法检索（BM25 / jieba）+ CLI

**1. 大致怎么做**
- 自己写一个 `while` 循环：把「问题 + 历史 + 工具清单 + 已有观察」发给 `deepseek-chat`，模型返回结构化 JSON 决策 `{action, args, reason}`；代码执行 `search` / `read_doc` / `ask_user` / `finish`，把结果回灌，直到 `finish` 或触达步数上限。
- 工具三个：`search(query, k)`（jieba 分词 + BM25 打分）、`read_doc(doc_id, section?)`、`ask_user(question)`（用于冲突澄清）。
- 冲突检测不是靠模型"觉得"，而是检索结果按条款聚合后发现同一字段数值不一致 → 模型被要求走 `ask_user`。
- 多轮：把上一轮的问题、检索到的 doc_id 和答案摘要存进会话，改写追问。
- 离线 Mock：`LLMClient` 抽象出一个接口，测试时注入 `FakeLLM`（按预设 action 序列回放），与真实路径共用同一套循环和工具代码。
- Trace：每步落 `examples/traces/*.jsonl`。

**2. 主要优点**
- 零外部依赖（`openai` SDK + `jieba`），完全离线可跑，评审 clone 即用。
- 循环逻辑全在自己手里，"是不是真 ReAct"一目了然，不会因为框架抽象被误读成固定分支。
- 替换 `data/` 文档后行为立即变化——天然满足"验伪"要求。
- 调试成本最低：一次运行就是一条线性日志，出错定位快。
- 3 小时内大概率能做完核心链路 + 全部证据材料。

**3. 主要风险**
- 词法检索对同义改写弱（"报销期限" vs "费用报销时间规定"）→ 需要让模型先生成 2–3 个查询变体再检索，否则"改写后的相似问题"这条验收点会挂。
- 中文分词质量依赖 jieba 词典，专有名词（制度编号、产品名）可能切碎 → 需要补一份自定义词典或对 doc_id / 编号做精确匹配兜底。
- 自己写循环容易在赶时间时退化成 `if 没检索到: 再检索` 的固定分支，反而踩红线。
- DeepSeek 的 function calling 偶有参数格式不稳，建议用 JSON 输出 + Pydantic 校验 + 一次重试，而不是裸依赖 tool_calls。

**4. 实现复杂度**：低。约 5–7 个文件、400–600 行，核心循环 <100 行。

**5. 可测试性**：高。LLM 可注入、工具是纯函数、状态是显式返回值；6 个验收场景 + 触顶 + 工具异常都能写成 pytest 断言，不依赖网络。

## 方案二：原生 ReAct + 混合检索（BM25 + 本地向量 + LLM 重排）

**1. 大致怎么做**
- 在方案一之上加检索层：`sentence-transformers` 加载 `bge-small-zh-v1.5`（首次运行下载约 100MB），把 FAQ 片段向量化；检索时 BM25 与向量分数加权融合，再让 `deepseek-chat` 对 Top-20 做一次相关性重排取 Top-5。
- 其余循环、工具、Mock、Trace 与方案一一致。

**2. 主要优点**
- 同义/口语化改写召回明显更好，"改写后的相似问题"这条最稳。
- "检索改进"是明确的高分项，混合检索 + 重排是最容易讲清楚、也最容易被验证的改进点。
- 对文档数量增长更鲁棒。

**3. 主要风险**
- 首次运行要下模型 + 装 torch，Windows 上 CPU 版依赖体积大，3 小时预算里可能吃掉 20–40 分钟且可能卡在网络上。
- 评审环境若离线，向量检索直接不可用 → 必须再做一条纯词法降级路径，等于多维护一套。
- 多一层黑盒，"分数融合权重"调不好反而比纯 BM25 差。
- 时间挤占会让证据材料（3 组 Trace、5 篇文档）做不完，而这是硬性交付。

**4. 实现复杂度**：中。检索层 +100~150 行，加上依赖与环境问题，实际风险高于代码量。

**5. 可测试性**：中。检索层可单测（给定语料查固定 query），但端到端复现依赖本地模型存在，评审机器上不一定成立。

## 方案三：LangGraph 状态图编排

**1. 大致怎么做**
- 用 `StateGraph` 定义 `agent → search / read / clarify → agent → finalize`，条件边由模型结构化输出决定；checkpoint 落 sqlite 存多轮会话。
- 检索、Mock、Trace 同方案一。

**2. 主要优点**
- 多轮会话、中断与人工澄清是框架现成能力，写起来省事。
- 图结构可视化，`02-solution.md` 里画出来观感好，评审读起来顺畅。
- 后续扩展（多 Agent、HITL）成本低。

**3. 主要风险**
- **最大风险是"看起来像固定流程"**。图一旦写死，评委很容易判定为"预设流程骨架 + 固定条件分支"，直接不满足 ReAct 要求。
- 框架版本 / API 变动、checkpoint 依赖、异步接口，都会在 3 小时内制造不可控的调试时间。
- 出问题时栈更深，定位成本高于手写循环。
- 框架名称不加分（题目明说），收益与风险不对称。

**4. 实现复杂度**：中高。代码量未必更多，但心智负担和调试不确定性最高。

**5. 可测试性**：中。节点可单测，但端到端要跑图，Mock 得适配框架的模型接口，测试写起来更绕。

## 对比一览

| 维度 | 方案一 原生+词法 | 方案二 原生+混合检索 | 方案三 LangGraph |
|---|---|---|---|

| 离线可跑 / 评审可复现 | 高 | 低（需下载模型） | 中 |
| 踩"假 ReAct"红线概率 | 低 | 低 | 中高 |
| 检索质量 | 中（可补救） | 高 | 取决于配置 |
| 换文档验伪 | 天然满足 | 天然满足 | 天然满足 |
| 调试成本 | 低 | 中 | 高 |
| 证据材料完成度 | 高 | 中 | 低 |

## 推荐：方案一

**理由（按"最稳交付"排序）**
1. 唯一能在 3 小时内把"核心循环 + 6 个验收场景 + 3 组 Trace + 5 篇文档"全部做完的路线，而材料齐全是硬性交付，缺一项就扣。
2. 无外部模型下载、无网络依赖，评审在任何机器上 clone 即跑；同时天然满足"无密钥走 Mock"这条硬约束。
3. ReAct 的真实性最容易被验证——循环是几十行显式代码，评委一眼能看出决策确实来自模型而非 if-else。
4. 换文档即变行为，天然通过"替换文档内容核对答案与动作"这一审核要点。

**为什么不选方案二**
它解决的是"检索召回不够"，但方案一可以用"模型生成查询变体 + 编号精确匹配兜底"以近乎零成本拿到 80% 的收益。方案二换来的边际效果，代价是模型下载、torch 安装、离线降级三条额外链路，在 3 小时预算下会直接挤压证据材料。**稳交付优先时，不该把时间押在环境上。**

**为什么不选方案三**
框架不加分，题目原文写得很清楚；而它带来的最大风险恰好是最致命的一条——图的固定性会被读成"预设流程"。同时调试不确定性高，时间不可控。**用框架换来的省事，不足以抵消踩红线的概率和调框架的时间。**

**方案一里必须额外做的两件事（否则仍会翻车）**
- 模型先做 **query 改写**（生成 2–3 个检索式），这是"改写后的相似问题"和"上下文追问"两条验收点的实际解法。
- 检索后做 **冲突聚合**（同字段多值 → 强制 `ask_user`），不要指望模型自觉。
