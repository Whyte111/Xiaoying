> 方案 C（确定性内核 + 受限模型决策点）。本文只定义结构、接口与边界，不含实现细节与代码。
> 状态：已定稿（6 处待定项由我按"最稳交付"择定，见 §8）。

## 1. 模块区分

```
src/
  domain/    纯领域：数据结构、规则检查、时段冲突、动作门控（无 IO、无模型、可纯单测）
  tools/     4 个业务工具（薄壳：参数校验 → domain/store → ToolResult）
  store/     草稿与排期存储（幂等 upsert、故障注入）
  agent/     决策层：动作集、循环、模型适配、脚本化假模型
  cli.py     唯一入口：加载用例 → 执行 → 输出结果字段 + trace 路径
  trace.py   JSONL 追加写入
tests/       domain 单测 + 六项验收点断言
examples/    3 组输入 / 实际输出 / trace
data/        合成素材、规则、已有排期
```

分层依赖**单向**：`cli → agent → tools → domain`，`tools → store`；`domain` 不依赖任何上层或 IO。

---

## 2. 目标结果

| 模块 | 目标（可被断言） |
|---|---|
| domain | 相同输入恒得相同结论；规则与冲突判定由测试全量覆盖 |
| tools | 4 个工具一律返回 `ToolResult`，**不向上抛异常** |
| store | N 次相同保存 → 恰好 1 份草稿；保存失败可注入且必返回失败 |
| agent | 每步恰好 1 个动作；到上限必返回 `LIMIT_REACHED`；trace 字段完整 |
| cli | 一条命令产出 5 个结果字段与 trace 文件路径 |

项目级目标（对应验收）：六项必测（正常 / 信息缺失 / 规则风险 / 时段冲突 / 重复提交 / 保存失败）全部有对应 trace 文件，且可由测试确定性复现。

## 3. 各模块职责

**domain/models** — 仅数据结构，无行为。

**domain/rules** — `check_rules`，只判不修，产出风险列表。

**domain/slots** — 区间重叠判定（含边界相接不算冲突）、按序生成替代候选、候选数量上限。

**domain/gating** — 由事实集合推导"当前允许动作集"，以此替代状态爆炸的 FSM；非法动作在此被挡掉。

**tools/** — `read_material` / `check_rules` / `query_slots` / `save_draft`，各一文件；入参出参过 schema 校验，错误一律转 `ToolResult(ok=False)`。

**store/** — 草稿 upsert（幂等键 + revision 递增）、已有排期只读、故障注入开关；单文件 JSON + 原子写。

**agent/loop** — 单步推进：取动作 → 校验合法 → 执行工具 → 写 trace → 更新 facts → 判终止或上限。

**agent/policy** — 确定性兜底策略；无模型时即离线 Mock 的决策源。

**agent/llm** — 模型适配，只接收 facts 摘要 + 允许动作集，只输出"动作名 + 参数"。

**agent/scripted** — 按序返回动作的假模型，供测试与离线演示，与真模型共用同一循环。

## 4. 核心接口

```python
# domain
check_rules(m: Material, rules: list[Rule]) -> list[RiskFinding]
find_conflicts(slot: Slot, existing: list[ExistingSlot], window: int) -> list[Conflict]
suggest_alternatives(slot: Slot, existing: list[ExistingSlot], limit: int) -> list[Slot]
allowed_actions(facts: Facts) -> set[Action]

# tools（统一返回，不抛异常）
read_material(material_id: str) -> ToolResult
check_rules(m: Material) -> ToolResult
query_slots(slot: Slot, window: int) -> ToolResult
save_draft(d: Draft) -> ToolResult            # upsert，幂等

# store
get_draft(material_id: str) -> Draft | None
upsert_draft(d: Draft) -> SaveOutcome          # created | idempotent | updated | failed

# agent
decide(facts: Facts, allowed: set[Action]) -> Action     # 模型或策略
run(req: RunRequest, lim: Limits) -> RunResult           # 上限在此强制
```

## 5. 关键数据结构

```python
Material(id, title, body_ref, requested_slot, owner, raw_complete)
Rule(id, kind, severity, msg)
Slot(start: datetime, end: datetime)          # 单一时区、分钟精度、不跨天
ExistingSlot(id, slot, owner)
RiskFinding(rule_id, severity, msg, field)
Conflict(slot, against_id, kind)
PendingItem(kind, question, blocks_save: bool)
Draft(material_id, revision, suggested_slot, pending, risk, created_at, updated_at)
ToolResult(ok: bool, code: str, data, err)    # OK | NOT_FOUND | INVALID | SAVE_FAIL
Facts(material?, rules_checked?, conflicts?, draft?, attempts: int)
StepRecord(step, action, args, result_summary, rationale)
ItemResult(audit_status, risk_reasons, suggested_slot, pending_items, draft_status)
RunResult(status: RunStatus, per_material: list[ItemResult], trace_path)
RunStatus = DONE | NEEDS_CONFIRM | NEEDS_INFO | BLOCKED | FAILED | LIMIT_REACHED
```

**输出 5 字段与内部状态的映射**（这是评审直接看的东西）：

| 输出字段 | 来源 |
|---|---|
| 审核状态 | `raw_complete` + `RiskFinding.severity` → PASS / NEED_INFO / BLOCKED |
| 风险原因 | `list[RiskFinding].msg` |
| 建议时段 | `requested_slot` 无冲突则原值；否则 `suggest_alternatives` 首选 |
| 待确认项 | `list[PendingItem]`（改动硬性要求、warn 级风险、时段变更） |
| 草稿保存状态 | `SaveOutcome` → SAVED_CREATED / SAVED_IDEMPOTENT / SAVED_UPDATED / FAILED / NOT_SAVED |

## 6. 主链路顺序

1. `cli` 读用例 → 构造 `RunRequest`（含 `Limits`）
2. `read_material` → 校验必填字段（ID / 标题 / 请求时段）
3. `check_rules` → 有 `block` 风险即阻断；`warn` 转待确认
4. `query_slots` → 与已有排期做区间冲突检测
5. 有冲突 → `suggest_alternatives` 生成候选，交给决策层
6. 决策层**在 `allowed_actions(facts)` 内**选：补查 / 换时段 / 请求确认 / 阻断 / 保存 / 结束
7. `save_draft` → `SaveOutcome` 决定入状态（幂等命中不新增）
8. 回到 4–7，直到终止条件或 `Limits` 用尽
9. 汇总 5 字段 → 写 trace → 打印结果并返回 trace 路径

终止一律产出明确 `RunStatus`，不存在"静默停止"。

## 7. 权限、隔离与边界

- **无发布能力**：代码中不存在发布客户端；`save_draft` 只写草稿库。出现"已发布/已生效"表述即缺陷。
- **硬性要求只读**：`requested_slot` 不允许被写回；改动即产生 `PendingItem`，且确认状态为 `PENDING`。
- **模型最小权限**：只输出动作名 + 参数；无文件、无网络、无 store 直连；trace 只记决策依据摘要，不留思维链、不留密钥。
- **请求隔离**：除 store 外无进程内全局态；一个请求一个 `Facts`。
- **上限**：8 步 / 8 次工具调用；到限 → `LIMIT_REACHED`，**不写草稿**。
- **失败即失败**：`SAVE_FAIL` 最多重试 1 次（避免自动重试冒充决策），仍失败则 `FAILED`。
- **不保证并发**：单进程顺序执行；多进程并发写同一 store 未加锁，属已知限制。

## 8. 本轮我择定的 6 项（如与预期不符请直接改）

| # | 项 | 决定 | 理由 |
|---|---|---|---|
| 1 | 判重键 | **素材 ID 唯一 + revision 递增** | "每项素材一个建议时段"是单值语义；一素材多草稿会与输出字段自相矛盾。同素材再提交 = 幂等返回既有草稿；换时段 = 更新同一草稿并升 revision |
| 2 | 用户确认落地 | 本次运行只产 `PENDING`；另设 `--approve <material_id>` 模拟用户确认 | 一次 CLI 运行无法真等人；确认边界仍需可测 |
| 3 | 必填字段 | ID / 标题 / 请求时段 | 缺任一即 `NEEDS_INFO`，不猜、不补全、不保存 |
| 4 | 上限 | 8 步 / 8 次工具调用 | 够走完"冲突→候选→确认→保存"，且能稳定触发到限场景 |
| 5 | 存储 | 单文件 JSON + 原子写 | 零依赖，评审环境必能跑；SQLite 留作后续替换点 |
| 6 | 规则严重度 | `block` 阻断保存；`warn` 可保存但列待确认 | 与"不得虚报、不得越权"一致 |
