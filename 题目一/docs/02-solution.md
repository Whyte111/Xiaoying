# 02 设计

## 一句话

**模型只负责"这一步做什么"，能不能做、做到什么程度由确定性内核决定。**

## 分层

```
cli → agent（循环 / 决策源）→ tools → domain（纯函数）
                              ↘ store（单文件 JSON）
```

依赖单向，`domain` 不碰 IO、不碰模型，因此规则、冲突、门控都能被纯单测覆盖。

## 一次运行怎么走

1. `cli` 读参数，`Toolbox.load` 校验 `data/` 三个 JSON
2. 进入循环，每步：
   - `allowed_actions(facts)` 由当前事实算出**可行动作集**
   - `decide(facts, allowed)` 由决策源在集合内挑一个（越界则回退并留痕）
   - 执行动作（前四个动作调工具，其余是纯决策）
   - 写一条 trace，更新 facts
3. 终止：`end` / `block` / 工具故障 / 保存失败 / 步数或工具调用用尽
4. 汇总为五字段 + `RunStatus`

## 为什么这么设计

### 1. 动作门控，而不是让模型自由发挥

模型只能从 `allowed_actions` 里选。好处：

- 不会跳过规则检查直接保存
- 不会在冲突未处理时落草稿
- 模型跑偏（返回非法动作）时自动回退，不会把系统带沟里

代价：门控只剩一个动作时，模型没有选择余地——**骨架是预设的，分岔点才由模型决定**。
`M01`（冲突→换时段）与 `M03`（warn→先请求确认）就是两个真实分岔点，见 `examples/`。

### 2. 四个工具是薄壳，纵深防御在工具层

即使门控失效，`save_draft` 也会拒绝给不存在的素材建草稿。工具一律返回 `ToolResult`，不向上抛异常。

### 3. 判重按「素材 ID」，用指纹判断是否同一请求

- 键 = 素材 ID（一个素材一份草稿，符合"每项素材一个建议时段"）
- 指纹 = 审核状态 + 建议时段 + 待确认项 + 风险集合
- 指纹相同 → `idempotent`，不新增、revision 不变
- 指纹不同 → `updated`，revision +1

### 4. 失败语义单独成状态

早期版本把"工具挂了"报成到达上限、把"模型提前结束"报成保存失败，都是**方向相反的误导**。
现在各有独立状态：`TOOL_FAILED` / `INCOMPLETE` / `FAILED` / `LIMIT_REACHED`。

保存失败**不做自动重试**：自动重试属于"预设行为"，冒充不了决策；也避免第一次失败第二次成功、对外报成功。

### 5. 不引入框架

LangGraph / ADK 能省掉"步数上限、状态持久化"，但引入版本与学习成本，而这两样在本项目里各只要几十行。
题目也明确"框架名称不加分"。全项目零第三方依赖，评审环境一定跑得起来。

### 6. 存储用单文件 JSON

零依赖、可读、可 diff。代价是没有并发保护，见 `03-evaluation.md` 的限制表。

## 关键不变量

| 不变量 | 保障位置 |
|---|---|
| 建议时段 ≠ 请求时段 ⇒ 必有待确认 | `loop._build_draft`（自动补） |
| 不存在"发布"能力 | 全仓库无发布客户端 |
| 模型只能输出动作名，不能带参数 | `llm._parse` |
| 工具不抛异常 | `toolkit` 全部 `try/except → ToolResult` |
| 写盘失败不留脏数据 | `store.upsert_draft` 写前快照、失败回滚 |
| `end > start`、时区口径一致 | `Slot.__post_init__` |
