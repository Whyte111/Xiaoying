# 01 需求

## 用户

内容团队的排期负责人：手里有一批待发布素材，需要判断能不能发、发在什么时段、哪些地方要人工拍板。

## 目标

对每项素材产出一份**可确认**的排期结论：能否发、为什么、建议哪个时段、哪些点必须人工确认、草稿有没有真的存下来。

## 范围（做什么）

- 读取素材元数据与发布时间要求
- 按审核规则判风险（阻断 / 警告）
- 与已有排期做时段冲突检测，冲突时给出替代时段
- 只在概率意义上"最优"不需要：给出首个可用候选即可
- 保存草稿，重复提交不产生第二份
- 输出五字段：审核状态、风险原因、建议时段、待确认项、草稿保存状态

## 明确不做

- 不接真实发布系统，**只写草稿**
- 不做多素材批量调度与全局最优
- 不做 UI、不做线上部署
- 不做跨时区换算（项目按单一时区、分钟精度处理）

## 成功标准

| 标准 | 判定方式 |
|---|---|
| 正常素材可直接排期 | 无风险无冲突 → `DONE`，草稿保存，无待确认 |
| 冲突不改硬性要求 | 冲突 → 替代时段 + 待确认，绝不静默改时段 |
| 风险有明确处置 | block 阻断不落草稿；warn 可存但列待确认 |
| 重复提交幂等 | 同一请求两次只有一份草稿、revision 不涨 |
| 保存失败不虚报 | 失败返回 `FAILED`，磁盘无残留 |
| 达上限有明确未完成态 | 返回 `LIMIT_REACHED`，不静默停 |

## 与原始题目要求的对应

题目列出六项必验：正常排期、素材信息缺失、规则风险、时段冲突、重复提交、保存失败。
其中「规则风险」同时覆盖 warn（可存）与 block（阻断）两条分支。

## 需求层面的已知取舍

- 交互式"用户确认"未做回传接口：单次运行只产出 `PENDING`，确认动作由下游人工完成。
- 一素材一草稿（按素材 ID 判重）：同一素材的多个候选时段不并列保存，靠 revision 更新。
